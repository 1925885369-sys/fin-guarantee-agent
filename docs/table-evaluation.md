# 表格链路评测

评测脚本：[`scripts/evaluate_tables.py`](../scripts/evaluate_tables.py)。本文件记录评测方法、分层规则和**实际跑出来的数字**。数字均由本机实跑取得，命令与数据目录写在下面，可复现；跑不出来的项一律标注「待验证」，不填估计值。

## 评测什么

表格链路有四段可测：**渲染**（虚构案例 PDF 的表格长什么样）、**解析**（能不能把表还原成结构化对象）、**契约**（`TableBlock v1` 的安全不变量是否守得住）、**交付**（核对接口与三出口是否同一份数据）。`scripts/evaluate_tables.py` 覆盖前两段；契约与交付由 `tests/test_table_block.py`、`tests/test_report_tables.py`、`tests/test_table_review_api.py`、`tests/test_table_extraction.py` 的用例覆盖（含负例）。

## 评测方法

```bash
PYTHONIOENCODING=utf-8 PYTHONPATH=. APP_DATA_DIR=.data-probe-trackD python scripts/evaluate_tables.py
```

脚本只读材料、不写数据库，分两段：

**第一段——虚构案例计分。** 用 `bond_documents.generate_case_materials()` 在临时目录重新渲染六套虚构案例的 PDF，再用 `parsers.parse_document()` 解析，最后与 `case_table_gold()` 的金标比对。比对口径：

- **表格召回**：金标表是否都被定位到（按表型与顺序匹配）；
- **单元格准确率**：原始值与规范化值逐格精确比对，`-`（零）、`—`（无数据）、空白（空单元格）三者分开统计，不互相折算；
- **表名 / 单位命中**：靠「`单位：` 行的上一行是表名」这条位置规则锚定，命中即计；
- **续表**：跨页续表是否被识别为同一张表（不是同页的另一张表）；
- **待确认**：`status='needs_review'` 的表数——这个数字**越低越好**，它代表「解析器自己承认没把握」。触发条件是确定性置信度规则：缺表名 −0.4、缺单位 −0.15、行列退化（行数为 0 或列数 < 2）−0.5，低于 0.9 即待确认。

金标与抽取结果相互独立：抽取器不读案例定义、不查 `key_pages`、不查数据库，只看 PDF 本身。

**第二段——参考材料定位。** 对中邮、北投四份公开参考材料只统计「表格能否被定位」以及表名/单位/跨页/待确认的分布，不逐格比对（原因见下方分层规则）。

## 分层规则

| 材料 | 进入什么指标 | 为什么 |
| --- | --- | --- |
| 华辰等六套虚构案例 | 表格召回率、单元格准确率、表名/单位命中、续表识别 | PDF 由本仓库渲染器生成、金标由案例模型建立，两者独立且可逐格标注 |
| 中邮、北投公开参考材料 | 只做版式兼容与「表格能否定位」 | **未逐格人工标注**。没有金标就没有准确率，宁可不算，也不用未被校验的自动金标凑数 |
| 已删除的贷款案例 | 不重建、不进入任何债券汇总 | 历史回归保留，不作为当前能力宣称 |

分层不是"挑好看的说"：真实材料上的定位结果照样出现在下面的表里，包括不好看的那些。

六套案例的表格召回率与单元格准确率均为 1.0000，每套案例都命中表名、单位，每套都识别出 1 张跨页续表，没有一张表落入「待确认」。

**这个 100% 是什么、不是什么（必须如实说明）：**

- **它是**一个闭环回归：材料由本仓库的渲染器（`pdf_tables.py`）生成，金标由案例模型（`financial_statements.py`）建立，解析器（`table_extraction.py`）只看 PDF。所以它证明的是「渲染—解析」这条链在结构上自洽、且**任何一格被改坏都会被这条评测发现**——它是回归防线，不是泛化能力证明。
- **它不是**对第三方真实材料的准确率。真实材料的表名写法、无边框表、合并单元格、扫描页等，都不在这个 100% 的覆盖范围里。下面的参考材料部分才是这些情况的实测。
- 100% 的意义依赖**负例**：`tests/test_table_extraction.py` 里有篡改数值、换年度列、跨主体串值、缺前导块四组负例，用于证明金标比对确实会失败——没有负例的 100% 是空转。金标比对本身在负例上必须报错。

### 参考材料（只验证定位，不计入准确率）

| 材料 | 检出表数 | 含表名 | 含单位 | 跨页 | 待确认 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `demo-北投/募集说明书.pdf` | 81 | 59 | 59 | 27 | 23 |
| `demo-北投/信用评级报告.pdf` | 132 | 0 | 0 | 0 | 132 |
| `real-bond-zhongyou-2026-02/中邮03募集说明书.pdf` | 78 | 47 | 47 | 20 | 33 |
| `real-bond-zhongyou-2026-02/中邮03信用评级报告.pdf` | 37 | 0 | 0 | 0 | 37 |

**如实解读：**

- **募集说明书方向可用但不完整。** 中邮募集说明书 47/78 张表有表名与单位（60%），北投 59/81（73%），跨页续表能识别（20 / 27 张）。同时有 33 / 23 张表被标记待确认——这些表的表名或单位行没能恢复，解析器如实降级，没有硬猜。
- **评级报告方向目前只有"能看见"，还谈不上"能用"。** 两份评级报告分别检出 132 与 37 张表，但**含表名 0、含单位 0、跨页 0，且 100% 标记待确认**。按上面的置信度规则，缺表名与缺单位直接扣到 0.45，必然落入待确认。也就是说：这些表的表名前导块没有恢复出来，抽取结果既无法按表名锚定，也不满足「原表逐格可定位（页码 + 坐标）」的契约要求，不能当作可信数据使用。**这是一个已知的能力缺口，不是通过项**——真实场景下这些表需要人工标注或引入新的表头恢复策略。
- 报告评级的表格目前不来自参考材料解析，报告四章的系统表格全部由代码从已核验数据生成；因此这个缺口不影响当前报告交付，但它限定了「真实材料表格自动解析」的实际覆盖范围。

**口径差异提醒：** [`financial-table-structure-reference.md`](financial-table-structure-reference.md) 记录的是原始 `page.find_tables()` 检出量（中邮募集说明书 100 张、北投募集说明书 111 张），本脚本输出的是解析器**合并续表后**的表数（78 / 81）。两者口径不同，不能直接相减比对。

**复现注意：** 参考材料段读的是 `<APP_DATA_DIR>/demo_materials/`。用全新的探测目录跑（例如 `APP_DATA_DIR=.data-probe-trackD`）时该目录不存在，四份参考材料会全部显示「缺失」；虚构案例段的数字不受影响。上表数字是在把公开参考 PDF 只读复制进探测目录后跑出来的（`tests/conftest.py` 的 `_copy_materials()` 用同一套做法）。

## 与其他评测的关系

- 本文件只管**表格结构**（表能不能被找到、格子对不对得上）。
- 事实抽取、指标、规则、报告支持率的指标在 [`EVALUATION.md`](EVALUATION.md)，两者不混算：表格单元格准确率高，不代表事实抽取准确率高。
- 参考材料的真实原件不进入 Git 仓库（位于 `.data/demo_materials/`，已被 `.gitignore` 忽略）。

## 已知边界

- 无边框表格、扫描件（OCR 默认关闭）、纵向合并单元格的复杂表头：当前一律走 `needs_review`，不猜、不让模型补齐。
- 参考材料没有逐格金标，因此**中邮/北投的单元格准确率是待验证项**，本文件不给数字。
- 表格数量、待确认数量会随解析器版本变化；换版本时重跑本文件中的命令并更新上表，不要沿用旧数字。
